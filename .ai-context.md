# AI Context: OrderApi

This file provides a concise description of the project structure, design patterns, and dependencies to optimize context and token usage for future AI prompts.

---

## 🚀 Tech Stack & Dependencies
- **Core**: .NET 10.0 Web API (Minimal APIs)
- **Database**: Entity Framework Core (`10.0.10`) targeting MS SQL Server.
- **CQRS & Messaging**: MediatR (`14.2.0`) for internal command/query dispatching and in-memory event publishing (`INotification`).
- **Validation**: FluentValidation (`12.1.1`) integrated via MediatR Pipeline Behaviors.
- **RabbitMQ**: RabbitMQ — `IRabbitMqProducer` / `RabbitMqProducer` publishes events to RabbitMQ exchanges as JSON. Config keys: `RabbitMq__Host` (e.g., `localhost` or `rabbitmq`) and `RabbitMq__Port` (default is 5672).
- **Infrastructure**: Docker Compose (local dev) and Kubernetes manifests in `k8s/` — both run SQL Server, RabbitMQ + Management UI, and OrderApi.

---

## 🏛️ Architecture Overview
The application follows a clean CQRS (Command Query Responsibility Segregation) architecture handled via MediatR.

### Core Flows:
1. **Validation Pipeline**:
   - `ValidationBehavior<TRequest, TResponse>` intercepts all MediatR requests.
   - If any `AbstractValidator<TRequest>` is found, validation runs automatically.
   - Failures throw a `FluentValidation.ValidationException`, which is caught at the API layer (returning `Results.ValidationProblem`).
2. **Commands (Writes)**:
   - Command records implement `IRequest<TResponse>`.
   - Handlers implement `IRequestHandler<TCommand, TResponse>`.
   - Creation of resources triggers an event dispatched via MediatR's `IPublisher.Publish()`.
3. **Queries (Reads)**:
   - Query records implement `IRequest<TResponse>`.
   - Handlers implement `IRequestHandler<TQuery, TResponse>`.
4. **Events (Pub/Sub)**:
   - Events implement `INotification`.
   - Handlers implement `INotificationHandler<TNotification>`. Currently, `ConsoleOrderCreatedEventHandler` logs events to stdout.

## ☸️ Kubernetes Deployment (`k8s/`)

Manifests translated from `docker-compose.yml`. Apply with `kubectl apply -k k8s/`.
Full run instructions live in `k8s/README.md`.

### Topology
All three workloads run in the `orderoo` namespace behind `ClusterIP` Services.
In-cluster DNS names match the compose service names, so `Server=sqlserver,1433`
and `RabbitMq__Host=rabbitmq` work unchanged.

| Workload | Kind | Storage | Service ports |
| --- | --- | --- | --- |
| `sqlserver` | Deployment (1 replica, `Recreate`) | 5Gi PVC at `/var/opt/mssql` | 1433 |
| `rabbitmq` | Deployment (1 replica, `Recreate`) | 2Gi PVC at `/var/lib/rabbitmq` | 5672, 15672 |
| `orderapi` | Deployment (1 replica, `RollingUpdate`) | none | 8080 |

### Compose → Kubernetes translation decisions
1. **`depends_on: service_healthy` → initContainers.** Kubernetes has no
   dependency-ordering primitive. `orderapi` blocks on two busybox
   initContainers polling `sqlserver:1433` and `rabbitmq:5672`.
2. **Config split by sensitivity.** Non-secret env (`ASPNETCORE_*`,
   `RabbitMq__Host`/`Port`) lives in ConfigMap `orderoo-config`; the SA
   password, RabbitMQ credentials and the full connection string live in Secret
   `orderoo-secrets`. Both are injected via `envFrom`.
3. **`replicas: 1` on `orderapi` is load-bearing.** `Program.cs` runs
   `dbContext.Database.Migrate()` before `app.Run()`. EF Core migrations are not
   concurrency-safe, so scaling out requires extracting the migration into a
   one-shot Job and removing that call.
4. **TCP probes, not HTTP.** No `/health` endpoint exists, so `httpGet` probes
   would 404. Adding `AddHealthChecks()` + `MapHealthChecks("/health")` is the
   prerequisite for switching to HTTP probes with real dependency checks.
5. **`Recreate` on the stateful services.** Their PVCs are `ReadWriteOnce`; a
   rolling update would deadlock on volume attachment.
6. **`imagePullPolicy: IfNotPresent`** on `orderapi` — the image
   (`orderoo/orderapi:latest`) is built locally and never pushed to a registry.
   On kind it must additionally be loaded with `kind load docker-image`.

### Security caveat
`01-secrets.yaml` contains the same hardcoded dev credentials as
`docker-compose.yml`, committed in plain text. Kubernetes Secrets are
base64-encoded, not encrypted. Replace with an external secret source before
any shared or production cluster.
